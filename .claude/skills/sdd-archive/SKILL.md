## What this skill does

Closes the SDD (Spec-Driven Development) development cycle by archiving a feature whose implementation and verification have finished. It reads `verify-report.md` (generated by `sdd-verify`), evaluates all of its verdicts, and if every criterion is `pass`, it requests explicit human confirmation (Principle III of the repo's constitution), generates `state.yaml` with the 4 mandatory closure metadata fields (`feature`, `estado`, `fecha_archivado`, `resumen_verify`) and moves the feature's complete folder from `specs/<feature>/` to `specs/_archive/<feature>/` (creating `specs/_archive/` if it doesn't already exist).

## User Input

```text
$ARGUMENTS
```

If the argument is not empty, identify the feature to archive (accepting formats like `002-sdd-gap-skills` or `specs/002-sdd-gap-skills`). If it's empty, try to resolve the currently active feature in `specs/` (or ask the user for clarification if there is ambiguity between multiple active folders).

## Step 1 — Idempotency and edge-case check (previous archiving)

Before doing any further reads or processing:
1. Check whether the specified feature's folder was already moved previously to `specs/_archive/<feature>/` or is no longer in `specs/`.
2. Check whether `state.yaml` with `estado: archivada` already exists inside the feature directory (`specs/<feature>/` or `specs/_archive/<feature>/`).
3. **Behavior on re-execution**: If either of the above conditions holds, stop execution immediately and inform the user that the feature was already archived previously, reporting its state without repeating the file move or re-generating `state.yaml`.

## Step 2 — Inspecting `verify-report.md` and blocking evaluation (FR-005)

1. Locate and read the `verify-report.md` file inside the feature's folder (`specs/<feature>/verify-report.md`).
   - If `verify-report.md` **does not exist**, refuse to archive, explaining that the feature must be verified first by running `sdd-verify`.
2. Analyze the rows and verdicts reported in `verify-report.md` (`pass`, `fail`, `no verificable`).
3. **Blocking evaluation**:
   - If it detects **at least one criterion** marked as `fail` or `no verificable`:
     - **REFUSE TO ARCHIVE**.
     - List in detail, in the report, each of the criteria blocking the archiving, indicating their status (`fail` or `no verificable`) and the reason/detail reported in `verify-report.md`.
     - Stop the process without moving any files or modifying the repository structure.

## Step 3 — Explicit human confirmation gate (Principle III of the constitution)

1. If **all criteria** recorded in `verify-report.md` have a clean `pass` verdict:
2. **STOP AND ASK THE USER FOR EXPLICIT CONFIRMATION** before making any change to the file system (Principle III of the repo's constitution — non-negotiable, never skip this step).
   - Inform the user that the feature has passed all verifications with `pass`.
   - Detail the action to be performed: generation of `state.yaml` and moving the folder `specs/<feature>/` to `specs/_archive/<feature>/`.
   - Wait for the user's explicit response and authorization to continue.

## Step 4 — Generating `state.yaml` and moving to `specs/_archive/` (FR-006)

Once the action has been explicitly confirmed by the user:
1. Create the `state.yaml` file at the root of the feature's folder (`specs/<feature>/state.yaml`) containing exactly the 4 fields defined in `data-model.md`:
   ```yaml
   feature: "<NNN-nombre>"
   estado: "archivada"
   fecha_archivado: "<YYYY-MM-DD>"
   resumen_verify: "Todos los criterios verificados en pass (<N>/<N> pass)"
   ```
2. Ensure the destination directory `specs/_archive/` exists (create it if it doesn't).
3. Move the feature's complete folder from `specs/<feature>/` to `specs/_archive/<feature>/`.

## Step 5 — Closing report

Present the final summary to the user:
- Confirm that the feature's folder was successfully moved to `specs/_archive/<feature>/`.
- Show the contents of the generated `state.yaml` file.
- Notify that the Spec Kit tools (`/speckit-converge`, `/speckit-analyze`, etc.) continue to work normally on the folder in its new archived location.

## Notes

- **Traceability and versions**: Any change to this skill's structure or behavior requires updating `metadata.version` in this `SKILL.md` and adding the corresponding entry to `CHANGELOG.md` (Principle IV of the constitution).
- **Irreversible actions**: Moving folders to `specs/_archive/` changes the active location of the specs. The human confirmation guardrail in Step 3 is the mandatory safeguard required by Principle III of the constitution.
